# v0.4.0 release notes

**Tag once:** every repo below has merged its `release/v0.4.0` PR into
`main`. Then tag `main` in each repo and create the GitHub release from
this file's `## GitHub release body` section.

## Milestone

**Hardening and the AWS demo cluster.** The STAM-71 audit drilled the
platform the way a demo could break it: kill the broker mid-sale, poison a
topic, replay a refresh token, sign a victim in cross-site, restart
identity. It found six real defects (STAM-451 to STAM-456), all fixed with
a test that fails without the fix. The cluster Terraform moved from Azure,
which was never applied, to one AWS EC2 node running k3s for a one-week
demo (STAM-457, ADR-0008).

## How this release was cut

v0.3.0 was squash-merged, so `main`'s commit is not an ancestor of `Dev`
and a Dev→main PR conflicts in every file both touched. Each repo instead
got a `release/v0.4.0` branch: it starts at `main` with `Dev`'s tree, so
the squash lands `Dev` byte-for-byte with nothing resolved by hand. Before
building it I checked every file that differs: no file on `main` held
content `Dev` never had, except the org profile's architecture image,
which the `.github` release kept. Expect the same for v1.0.0 unless a
release is rebase-merged instead.

## GitHub release body

```markdown
# STAMPEDE v0.4.0 — hardening and AWS demo cluster

**Six defects found by drilling the platform the way a demo breaks it,
each fixed with a test that fails without the fix, and the cluster moved
to AWS for the demo week.**

## Fixed

### Events lost during a broker outage — STAM-451 (booking)
- The outbox marked rows published as soon as `send()` returned, before
  Kafka acked. A booking crash during a broker outage lost the buffered
  events for good. It now waits for each ack, stamps only the acked
  prefix, and uses the outbox row id as `eventId` so a resend is deduped.
  `OutboxBrokerOutageIT`; drill phase B went from 0/4 to 4/4 delivered.

### One bad record stalled a partition forever — STAM-452 (all consumers)
- A non-JSON record failed inside `poll()`, before the error handler, so
  the container re-polled the same offset forever (15–19k log lines a
  minute). Every consumer now wraps its deserializer in
  `ErrorHandlingDeserializer`. Catalog and booking dead-letter the original
  bytes; payment, notification and identity log and skip.

### Login CSRF — STAM-453 (identity)
- A hostile page could sign a victim's browser in as the attacker. The
  login form now carries a session-bound CSRF token; a cross-site POST is
  rejected.

### Every token died on an identity restart — STAM-454 (identity)
- A regenerated signing key kept a fixed `kid`, so validators kept the
  old key and 401'd everything. Identity now loads a persistent key
  (`IDENTITY_RSA_PRIVATE_KEY`) and uses its thumbprint as the `kid`.

### Frontend 502 after the gateway restarted — STAM-455 (frontend)
- nginx resolved `gateway` once at startup. It now re-resolves through
  Docker's DNS.

### Identity's own API ignored its tokens — STAM-456 (identity)
- `/api/**` sat on the form-login chain, so an ADMIN's JWT was treated as
  anonymous. It is now a JWT resource server: ADMIN 200, USER 403, none 401.

### Also
- Stripe's signed webhook gets through the gateway without a JWT
  (STAM-449); compose passes `STRIPE_WEBHOOK_SECRET`.
- Mailhog and SMTP NetworkPolicies on the cluster (STAM-450).
- snappy-java pinned to 1.1.10.9 for Trivy CVEs in every Kafka service.

## AWS demo cluster — STAM-457 (ADR-0008)
- Terraform for one `m6i.2xlarge` running k3s: Elastic IP for DuckDNS,
  80/443 public, 22 from the operator only, S3 state with native locking,
  a $100 budget alarm that ignores credits.
- Backups to S3 through the instance role: no static key anywhere.
- Fixed on the way: k3s' Traefik held 80/443 (ingress-nginx could never
  bind), and the Ingress and backup job pointed at a namespace nothing
  deploys to.

## Evidence
- `docs/hardening-audit.md` and `docs/hardening/evidence/`: before/after
  output for every fix, plus the drill scripts in `tools/hardening/`.

## Not included
- A live run on AWS. The Terraform validates, but the port scan, the
  readiness timing and the S3 restore wait for `terraform apply`.
- The 5,000-VU load test (STAM-70) and v1.0.0 (STAM-72).
```
